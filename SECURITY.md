# Security Policy & Threat Model

## Overview

NijiSamvad is built from the ground up as an end-to-end encrypted (E2EE) real-time communication platform engineered for ephemeral, private conversations with no database, no user accounts, and no persistent history.

---

## Technical Security Architecture

### 1. Cryptography & Key Derivation
- **Algorithm**: AES-256-GCM with unique 96-bit (12-byte) Initialization Vectors (IVs) generated via `crypto.getRandomValues()` for every single message and attachment chunk.
- **Unbiased Secret Generation**: Room secrets generated by the application use Web Crypto random sampling with rejection sampling to eliminate modulo bias across a 68-character high-entropy alphabet ($68^{24} \approx 2^{146}$ entropy).
- **Secret vs. Room Name Entropy**: Message confidentiality and cryptographic room isolation depend strictly on the entropy of the **Room Secret**, not the Room Name. The Room Name serves as routing metadata, while the Room Secret derives all cryptographic keys.
- **Key Derivation**: PBKDF2 with 100,000 iterations and SHA-256 hashing using Web Crypto APIs.
- **Secret Isolation**:
  - `encryptionKey` is derived with salt `encryption_salt_<roomName>` and remains strictly inside client memory.
  - `authHash` is derived with salt `auth_salt_<roomName>`. The server receives ONLY `authHash` for room authorization.
  - Under stated cryptographic assumptions (PBKDF2-SHA256 with 100,000 iterations), the server cannot feasibly compute `encryptionKey` or recover the original room secret from `authHash`.
  - Constant-time comparison (`crypto.timingSafeEqual`) is enforced on `authHash` validation to prevent timing side-channel attacks.
- **Attachment Encryption**: Files are encrypted on the client with independent, cryptographically random AES-256-GCM keys before upload. The server stores opaque binary ciphertext blobs.

### 2. Ephemeral Storage & Room Teardown
- **Zero Database**: No persistent database or storage engine is used.
- **Ephemeral Wiping**:
  - Ephemeral attachment uploads are wiped clean on server startup and graceful shutdown (`SIGTERM`/`SIGINT`).
  - When the last participant leaves a room, all associated attachment files are deleted from disk, and in-memory room references are destroyed.

### 3. Socket.IO & WebRTC Signaling Security
- **Room Authorization**: All socket actions (`send`, `typing`, `message-reaction`, `webrtc-*`, `call-*`) verify socket room membership. Cross-room signaling or messaging is rejected.
- **Rate Limiting**: Throttles messaging, reactions, typing, and WebRTC signaling per socket to prevent flooding or abuse.
- **Input Sanitization**: Basic HTML tag stripping (`<>`) on usernames and room names to mitigate XSS vectors. Messages and UI content are rendered as plain text via React DOM escaping.

## Threat Model & Security Boundaries

### Protected Assets
1. **Message & Attachment Plaintext**: Encrypted on client before leaving browser memory.
2. **Room Secrets & Encryption Keys**: Kept exclusively in client memory; never sent to server.
3. **Room Isolation**: Cryptographically enforced via distinct PBKDF2 salts and authHashes.

### Security Guarantees
- **Server Confidentiality**: The server operator cannot decrypt message or attachment content under stated cryptographic assumptions.
- **Passive Eavesdropper**: Network traffic is encrypted with TLS (HTTPS/WSS) and application-layer AES-256-GCM E2EE.

### Operational Metadata & Limitations
- **Server Metadata Visibility**: The server naturally observes operational metadata required for routing: IP addresses, connection timestamps, room names, active member rosters, and ciphertext payload sizes.
- **Endpoint Compromise**: If a user's browser or device is compromised (e.g., malicious browser extension with DOM access or keylogger), in-memory plaintext can be captured.
- **Network NAT Limitations**: Standard WebRTC P2P direct connection is used. On restrictive symmetric NATs or corporate firewalls without TURN relays, WebRTC media streams may fail to connect.
- **Small Group Scaling**: Mesh calling scales as $O(N^2)$ connections; designed for small-group calls rather than large-scale broadcasts (no SFU).
- **Provider-Level Ephemeral Backups**: While the application deletes files immediately upon room teardown, infrastructure providers (e.g., cloud platforms) may retain disk snapshots or access logs outside application control.

If you discover a potential security issue in NijiSamvad, please report it directly via GitHub Security Advisories or by contacting the project maintainers.
